# v0.1 Baseline Architecture Review

## Purpose

This baseline is a safety-first security evidence harness for repeatable audits. It is intended to turn ad hoc security checks into structured modules with explicit safety metadata, private runtime evidence, sanitized reporting, and project-local security-map integration.

Cheddar is the first adapter and proving ground, but Cheddar-specific behavior lives under `src/pentest_harness/adapters/cheddar/`. The core package is meant to remain reusable across projects.

## Storage Model

The harness separates storage into three domains:

| Domain | Contents | Commit Policy |
|---|---|---|
| `pen-test` repo | reusable code, templates, docs, tests, adapters | committed |
| target repo `.security/` | sanitized security map, rules of engagement, attack surface, trust boundaries, flow docs, invariant docs, safe finding stubs | committed in the target repo only |
| `/tmp/security-harness/runs/<project>` | private runtime ledger, artifacts, generated reports, and sensitive evidence when explicitly needed | never committed |

## Safety Model

Evidence levels:

- `observe_only`: static or passive review only. No HTTP requests.
- `non_mutating_probe`: safe HTTP checks that should not change application state.
- `safe_mutation`: controlled changes against staging or approved test resources.
- `controlled_exploit`: real vulnerability proof with explicit authorization, scope, impact cap when relevant, and private runtime evidence.

Safety levels:

- `static_only`
- `http_safe`
- `credentialed`
- `state_changing`
- `destructive`

Production gates:

- `--allow-production` is required.
- `--authorization-ticket <ticket>` is required.
- `--evidence-level` must be explicitly provided.
- Module metadata must set `production_allowed=true`.
- Target must be allowed by adapter profile or `.security/rules-of-engagement.md`.
- Money-impact modules require an impact cap such as `--max-impact-cad`.

State-changing and destructive gates:

- State-changing or destructive modules require explicit metadata.
- They require `--approve-state-change`.
- They must use an appropriate evidence level such as `safe_mutation` or `controlled_exploit`.

Target guard behavior:

- Unknown targets fail closed.
- Staging validation only considers staging allowlists.
- Production validation only considers production allowlists and production gates.
- Adapter-level forbidden URLs remain separate from environment allowlists.
- Cheddar's legacy staging host is explicitly forbidden by the Cheddar adapter.

## `.security` Integration

The harness can read target repo `.security/` folders as sanitized security maps.

Current readers support:

- `.security/rules-of-engagement.md`
- `.security/attack-surface.md`
- `.security/methodology.md`
- `.security/trust-boundaries.md`
- `.security/findings/TEMPLATE.md`
- `.security/flows/*.md`
- `.security/invariants/*.md`
- `.security/webhooks/*.md`

The harness can propose or write only sanitized `.security` content:

- route or surface drift summaries
- TODO/checklist items
- sanitized finding stubs
- invariant coverage summaries
- links to relevant docs or private runtime run IDs

The harness must never write these to `.security/`:

- secrets
- auth headers
- cookies
- webhook signatures
- raw request bodies
- raw response bodies
- private keys
- seed phrases or mnemonics
- database dumps
- customer PII
- production object IDs
- screenshots with sensitive data
- replayable exploit payloads or PoCs

The reusable generic template lives at:

```text
templates/security-folder/
```

## Current Modules

- `route-inventory`: static source scan for route declarations.
- `security-map-drift`: compares static route inventory against the target repo `.security/attack-surface.md` baseline and proposes a sanitized drift summary.
- `webhook-negative`: Cheddar adapter module that runs safe bad/missing-auth webhook probes against staging.
- `checkout-exposure-summary`: Cheddar adapter module that normalizes existing private checkout exposure evidence into a safe ledger/report summary.

## Current Cheddar Behavior

Staging:

- Current allowed API target is `https://staging-api-aws.cheddar.biz`.
- Cheddar staging route and webhook behavior is implemented only in the Cheddar adapter.

Forbidden legacy staging:

- `https://staging-api.cheddar.biz` is forbidden by the Cheddar adapter because it is the legacy/wrong staging endpoint for this workflow.

Production:

- Production support exists as a gated framework path.
- No production-capable modules are enabled yet.
- The current Cheddar modules are staging/static only.

## Validation

Commands:

```bash
PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=src python3 -m unittest discover -s tests -v
grep -R -i "cheddar\\|staging-api\\|coinflow\\|quicknode\\|svix" templates/security-folder || true
```

Current results:

- Unit tests: 14 tests passed.
- Generic template grep: no output, meaning the generic template does not contain the checked Cheddar-specific strings.

## Known Limitations

- Route drift is approximate. The current scanner finds local route declarations but does not fully reconstruct framework mount prefixes or all GraphQL/job/worker surfaces.
- Markdown parsing is convention-based, not a complete Markdown or framework parser.
- Custom target override is not implemented yet.
- No production-capable modules exist yet.
- No raw evidence export is implemented; export is sanitized by design.
- No CLI command exists yet to initialize a target repo `.security/` folder from `templates/security-folder/`.

## Recommended Next Steps

1. Add `pentest security-map init` to copy the generic template into a target repo safely.
2. Review artifact, ledger, report, export, and `.security` write paths as one end-to-end redaction flow.
3. Improve route mount reconstruction and reduce drift noise.
4. Add a finding lifecycle model for candidate, likely, confirmed, fixed, duplicate, and accepted-risk states.
5. Only after those safety and review paths are tightened, add additional Cheddar probes.
